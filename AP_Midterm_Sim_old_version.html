سؤالان مقاليان — أحدهما برسم UMLTwo essays — one with a UML drawing

نمط د. بيداء: سؤالان، أحدهما يطلب رسم تصميم UML لأحد الأنماط مع شرح المشاركين والعلاقات. تدرب على الرسم بورقة قبل الاختبار.Dr. Bidaa's format: two questions, one asks for a UML drawing of a design pattern with participants explained.
Q1
اشرح نمط الـAdapter، وارسم تصميم UML يوضّح المشاركين والعلاقات بينهم، مع مثال عملي.Explain the Adapter pattern, draw a UML of its participants and relationships, with a practical example.

التعريف · Definition: نمط إنشائي (Structural) يسمح لواجهتين غير متوافقتين بالعمل معاً، يعمل كمترجم (Translator) يحوّل طلبات من واجهة لأخرى دون تعديل أي من الطرفين.A Structural pattern that lets two incompatible interfaces work together by acting as a Translator — converting requests without modifying either side.

المشاركون · Participants (4):

  • Client — يستخدم النظام ويتوقّع واجهة معينة (ITarget).
  • ITarget (Interface) — الواجهة المتوقّعة من العميل (مثل IPaymentProcessor).
  • Adapter — يطبّق ITarget ويحوي مرجعاً للـAdaptee، يحوّل الطلب (مثل StripeAdapter).
  • Adaptee (Legacy/3rd-party) — الكلاس القديم بواجهة مختلفة (مثل StripeGateway).

متى يُستخدم · When to use: عند دمج مكتبات خارجية أو أنظمة قديمة بلا تعديل كودها؛ توفير واجهة موحّدة لتطبيقات مختلفة. مثال واقعي: محوّل كهرباء.

الرسم · UML Class Diagram:

┌─────────┐ uses ┌──────────────────────┐ │ Client │ ─────────────────────▶ │ «interface» ITarget │ └─────────┘ │ + Request() │ └──────────▲─────────────┘ │ implements ┌──────────┴─────────────┐ │ │ ┌─────────┴────────┐ (other adapters...) │ Adapter │ │ - adaptee: Adaptee│ │ + Request() │ │ → adaptee.SpecificRequest() └─────────┬─────────┘ │ has-a (holds reference) ▼ ┌──────────────────────┐ │ Adaptee (Legacy) │ │ + SpecificRequest() │ └──────────────────────┘

مثال · Example: تطبيق يتوقّع IPaymentProcessor.Pay() لكن Stripe توفّر StripeGateway.ProcessStripePayment(). الـStripeAdapter يطبّق IPaymentProcessor ويحوّل Pay() إلى ProcessStripePayment(). العميل لا يتواصل مباشرةً مع Stripe — مع Adapter فقط.

Q2
اشرح نمط الـDecorator، وارسم تصميم UML، مع ذكر المشكلة التي يحلّها ولماذا يُفضّل على الوراثة (Inheritance).Explain the Decorator pattern, draw its UML, state the problem it solves, and why it's preferred over Inheritance.

التعريف · Definition: نمط إنشائي يضيف سلوكاً جديداً لكائن ديناميكياً (وقت التشغيل) دون تعديل الكود المصدري للكلاس، عبر تغليفه بطبقات (wrappers).A Structural pattern that adds behavior dynamically at runtime without modifying the source class, by wrapping it in layers.

المشكلة · The Problem: محرّر نصوص يدعم Bold/Italic/Underline بكل التركيبات. بالوراثة نحتاج كلاس لكل تركيبة (BoldText, BoldItalicText...) = انفجار في عدد الكلاسات، صعب الصيانة، ويخالف Open/Closed Principle.

لماذا Decorator بدل Inheritance: الوراثة ثابتة (compile-time) وتنتج كلاسات كثيرة؛ الـDecorator ديناميكي وكل decorator مسؤولية واحدة، يمكن تركيبها بأي ترتيب بأقل عدد كلاسات.

المشاركون · Participants: IText (interface) · PlainText (concrete) · TextDecorator (base) · BoldDecorator / ItalicDecorator / UnderlineDecorator.

الرسم · UML:

┌─────────────────────────┐ │ «interface» IText │ │ + Render() │ └──────────▲──────────────┘ │ implements ┌──────────────┴───────────────┐ │ │ ┌──────────┴──────────┐ ┌──────────────┴───────────────┐ │ PlainText │ │ TextDecorator │ │ + Render() │ │ - component: IText │ │ → "plain text" │ │ + Render() → component.Render()│ └──────────────────────┘ └──────────────▲───────────────┘ │ extends ┌───────────────────┼───────────────────┐ │ │ │ ┌─────────┴─────────┐ ┌───────┴─────────┐ ┌───────┴─────────┐ │ BoldDecorator │ │ItalicDecorator │ │UnderlineDecorator │ │+Render(){ │ │+Render(){ │ │+Render(){ │ │ component.Render();│ │ component.Render();│component.Render();│ │ add <b>..</b>} │ │ add <i>..</i>} │ │ add <u>..</u>} │ └───────────────────┘ └─────────────────┘ └─────────────────┘ Stacking: Client → Underline → Italic → Bold → PlainText Output: <u><i><b>Hello</b></i></u>

متى يُستخدم · When to use: إضافة سلوك ديناميكي · تجنّب كثرة الكلاسات الفرعية · تركيبات ميزات · توسيع بلا تعديل مصدر. مثال: إضافات القهوة.

تدريب إضافي: ارسم بنفسك Adapter و Decorator و Facade على ورقة قبل الاختبار — الرسم هو الذي يفرّق في درجة السؤال. راجع تبويب «Patterns» للبقية.

أسس البرمجة الكائنية و مبادئ SOLID Programming Foundations — OOP & SOLID

لماذا البرمجة المتقدمة؟ المشاريع الصغيرة (حاسبة، إدارة درجات) لا تعكس تعقيد الأنظمة الحقيقية مثل Facebook و Amazon و الأنظمة البنكية التي تخدم ملايين المستخدمين. الهدف: التحوّل من مبرمج إلى مهندس برمجيات قادر على بناء أنظمة قابلة للتوسّع، آمنة، وسهلة الصيانة. Transform from programmers into software engineers building scalable, maintainable, secure systems.

أركان OOP الأربعة · The 4 Pillars of OOP

Encapsulation
تغليف البيانات داخل الكلاسات وإخفاؤها. يقلّل التعقيد ويزيد إعادة الاستخدام.
Abstraction
إظهار ما يلزم فقط وإخفاء التفاصيل الداخلية. يبني واجهات أبسط.
Inheritance
إعادة استخدام خصائص وميثودات الكلاس الأب. يمنع تكرار الكود.
Polymorphism
تعدّد الأشكال: نفس الميثود تتصرف بشكل مختلف حسب الكائن.

معدّلات الوصول في C# · Access Modifiers

  • public — الجميع يستطيع الوصول.
  • private — هذا الكلاس فقط.
  • protected — هذا الكلاس + الكلاسات الابنة.
  • internal — نفس المشروع فقط.

مبادئ SOLID الخمسة · The 5 SOLID Principles

هدفها المشترك: بناء أنظمة مرنة وقابلة للصيانة.

S · Single Responsibility · مسؤولية واحدة الكلاس يكون له سبب واحد فقط للتغيير. مثال سيّئ: كلاس Employee يحوي calculatePay() + reportHours() + save() — كل قسم (محاسبة/موارد بشرية/قواعد بيانات) يعدّله لأسباب مختلفة، فيسبب تعارضات. الحل: افصلها لـ PayrollCalculator و HoursReporter و EmployeeRepository.
O · Open/Closed · مفتوح للإمتداد، مغلق للتعديل صياغة Bertrand Meyer 1988: يجب أن يكون النظام قابلاً للتوسيع دون تعديل الكود الموجود. مثال: نظام يعرض ملخّصاً مالياً على صفحة ويب، ثم طُلب تقرير مطبوع بنفس البيانات. الحل: افصل المسؤوليات (Controller/Interactor/Presenters/Views) فتضيف مخرج PDF جديداً دون لمس منطق العمل.
L · Liskov Substitution · استبدال لیسکوف الكلاس الابن يجب أن يحلّ محلّ الأب دون كسر السلوك. مثال كلاسيكي: Bird → Sparrow ✓ يطير، لكن Penguin ✗ لا يطير = كسر العقد. الوراثة السيّئة تلوّث البنية بآليات إضافية.
I · Interface Segregation · فصل الواجهات لا تُجبر الكلاسات على تطبيق ميثودات لا تحتاجها. بدل واجهة كبيرة (Robot يُجبر على eat())، افصلها لواجهات صغيرة: IWorkable و IEatable. الفائدة: واجهات أصغر، اقتران أقل، صيانة أسهل.
D · Dependency Inversion · عكس الاعتمادية منطق العمل عالي المستوى يجب أن يعتمد على التجريدات (interfaces) لا التطبيقات الملموسة. الكائنات الملموسة يجب أن تُنشأ في مكان ما، لكن النواة تتعامل مع interfaces فقط. (هذا أساس Clean Architecture في L5.)

مقدمة في أنماط التصميم + الأنماط الإنشائية Design Patterns Intro & Creational Patterns

مشاكل التصميم السيّئ تكرار الكود · كلاسات ضخمة · اقتران محكم (Tight Coupling) · صعوبة الاختبار والصيانة والتوسيع. كلما كبر النظام، أصبح التصميم الجيد ضرورياً.

ما هو الـDesign Pattern؟ · What is a Design Pattern?

ليس لغة برمجة، ولا framework، ولا مكتبة، ولا كود جاهز. Pattern ≠ Code. بل هو مخطط (Blueprint) — حلّ مجرّب وقابل لإعادة الاستخدام لمشكلة تصميمية متكررة. مثل مخطط البناء قبل البناء نفسه. A proven, reusable solution to a recurring software design problem. Like a blueprint, not the building itself.

تاريخ الأنماط · History — Gang of Four

1994: أربعة مهندسي برمجيات نشروا كتاب «Design Patterns: Elements of Reusable Object-Oriented Software» فعُرفوا بـ Gang of Four (GoF). صنّفوا 23 نمطاً في ثلاث فئات:

Creational · إنشائية
تركّز على كيفية إنشاء الكائنات. Singleton, Factory Method, Abstract Factory, Builder, Prototype.
Structural · هيكلية
تركّز على كيفية تركيب الكلاسات والكائنات. Adapter, Facade, Decorator, Proxy, Composite, Bridge.
Behavioral · سلوكية
تركّز على كيفية تفاعل الكائنات. Strategy, Observer, Command, State, Iterator.

لماذا نحتاج Creational Patterns؟ · Why Creational?

عندما نحتاج إنشاء كائنات كثيرة، هل ينشئ كل كلاس كائناته بنفسه؟ عادةً لا. إنشاء الكائنات يجب أن يُدار بعناية — وهذا دور الأنماط الإنشائية.

1) Singleton Creational

التعريف: نمط إنشائي يضمن أن يكون لكلاس ما نسخة واحدة فقط مع توفير نقطة وصول عامة لها.

⚠️ ملاحظة مهمة Singleton يحلّ مشكلتين في آنٍ واحد، لذلك يخالف Single Responsibility Principle: (1) ضمان نسخة واحدة + (2) توفير نقطة وصول عامة.

الخطوتان الأساسيتان:

  1. اجعل الـconstructor الافتراضي private لمنع الكلاسات الأخرى من استخدام new.
  2. أنشئ static creation method تستدعي الـconstructor الخاص مرّة، تخزّن الكائن في حقل ثابت، ثم تُعيده في كل مرة. 
public class Logger
{
    private static Logger _instance;
    private Logger() { } // منع new من الخارج

    public static Logger GetInstance()
    {
        if (_instance == null)
            _instance = new Logger();
        return _instance;
    }
}
✓ استخدمه في
  • Logger
  • Configuration Manager
  • Cache Manager
  • Database Connection
  • Printer Spooler
  • Application Settings
✗ لا تستخدمه في
  • Student
  • Employee
  • Product
  • Customer
  • Order
  • (كل ما يحتاج نسخاً متعددة)

2) Factory Method Creational

التعريف: نمط إنشائي يوفّر واجهة لإنشاء كائنات في superclass، لكن يسمح للـsubclasses بتغيير نوع الكائنات المنشأة. بدل new المباشر، يفوّض الإنشاء لـmethod مخصّصة → اقتران ضعيف (loose coupling) وقابلية توسّع.

Client → Factory ─creates─▶ Product (not new directly)
✓ متى تستخدمه
  • عندما لا تعرف الأنواع الدقيقة مسبقاً (Unknown Subclasses).
  • مركزية منطق الإنشاء المعقّد.
  • تسهيل الاختبار عبر mock objects.
✗ لا تستخدمه
  • للأنواع البسيطة الثابتة.
  • إذا كان الإنشاء بسيطاً جداً.

الأنماط الهيكلية + UML (الأنماط الأربعة المطلوبة للرسم) Structural Patterns + UML — the four drawing-required patterns

الأنماط الهيكلية تركّز على العلاقات، التركيب، تعاون الكائنات، المرونة، وإعادة الاستخدام. تستخدم Interfaces و Inheritance و Composition، وأغلبها يفضّل Composition على Inheritance.

Inheritance
علاقة IS-A: الكلب هو حيوان.
Composition
علاقة HAS-A: السيارة لها محرك. (الأفضل.)

تنبيه L3 المهم: كل نمط يحلّ مشكلة هيكلية مختلفة، واختيار النمط الصحيح يعتمد على المشكلة لا على التفضيل الشخصي. بدل تعديل الكلاسات الموجودة، الأنماط الهيكلية تعيد تنظيم العلاقات بينها.

1) Adapter — المترجم Structural

التعريف: يسمح لواجهتين غير متوافقتين بالعمل معاً، يعمل كجسر يحوّل واجهة لأخرى. Adapter = Translator.

مثال واقعي محوّل شاحن هاتف أوروبي في مقبس بريطاني — لا تغيّر الهاتف ولا المقبس، فقط تستخدم محوّلاً يحوّل الشكل. المحوّل يغيّر الاتصال، لا الأجهزة.

السيناريو: خدمة بريد قديمة LegacyEmailService.SendEmail()، لكن تطبيقنا الجديد يتوقّع IMessageService.Send(). الأسماء مختلفة → الواجهتان غير متوافقتين.

الحل: أنشئ EmailAdapter يطبّق IMessageService، يحوي مرجعاً للـLegacy، ويحوّل Send() إلى SendEmail().

Client │ Pay(250) ▼ StripeAdapter (implements IPaymentProcessor) │ ProcessStripePayment(250) ▼ StripeGateway (Legacy / 3rd-party) ★ العميل لا يتواصل مباشرةً مع Stripe/PayPal

المشاركون (4):

Client
يستخدم النظام ويتوقّع واجهة معيّنة.
ITarget
الواجهة المتوقّعة (interface).
Adapter
يطبّق ITarget ويحوّل الطلبات للـAdaptee.
Adaptee
الكلاس القديم/الخارجي بواجهة مختلفة.
✓ استخدمه عند
  • واجهتان غير متوافقتين.
  • دمج مكتبات/أنظمة قديمة بلا تعديلها.
  • إعادة استخدام كلاس في تطبيق جديد.
  • توفير واجهة موحّدة لتطبيقات مختلفة.
✗ لا تستخدمه عند
  • الواجهتان متوافقتان أصلاً.
  • يمكن تعديل الكلاس بسهولة.
  • إعادة هيكلة بسيطة تحلّ المشكلة.

2) Facade — الواجهة المبسّطة Structural

التعريف: يوفّر واجهة مبسّطة واحدة لنظام فرعي معقّد. العميل يتواصل مع الـFacade فقط، لا مع الـsubsystems.

مثال واقعي «شاهد فيلم» بضغطة واحدة تشغّل TV + نظام الصوت + مشغّل + تختار HDMI + تخفّض الإضاءة. الـFacade يحوي كل هذه الخطوات داخله.

المشكلة بلا Facade: في نظام تسوّق، عند «تأكيد الطلب» يجب: التحقّق → معالجة الدفع → تحديث المخزون → إنشاء فاتورة → إرسال إيميل. العميل يتواصل مع 5 خدمات مباشرة = اقتران محكم + كود معقّد + صعوبة صيانة.

Client │ PlaceOrder() ▼ ShoppingFacade ★ العميل لا يعرف الـsubsystems ├─▶ OrderService ├─▶ PaymentService ├─▶ InventoryService ├─▶ InvoiceService └─▶ EmailService

الفكرة الجوهرية: الـFacade يعرف الـsubsystems، لكن العميل لا يعرفها.

3) Proxy — الوكيل/البديل Structural

التعريف: يوفّر بديلاً (placeholder/surrogate) لكائن آخر للتحكم في الوصول إليه. العميل يتواصل مع الـProxy الذي يقرر كيف ومتى الوصول للكائن الحقيقي.

مثال واقعي — بطاقة ATM لسحب المال لا تصل حسابك مباشرة، بل تستخدم بطاقة ATM. البطاقة تتحقّق من هويتك، تفحص الـPIN، تسمح أو ترفض، ثم تتواصل مع حسابك.

أسباب استخدامه: الأمان · الأداء · التحميل الكسول (Lazy Loading) · التخزين (Caching) · التسجيل (Logging) · الوصول البعيد (Remote).

Client │ Withdraw() ▼ BankAccountProxy (authenticated?) │ ───── has-a ─────▶ BankAccount (real)

4) Decorator — المزخرف/الملفّف Structural

التعريف: يضيف سلوكاً جديداً لكائن ديناميكياً (وقت التشغيل) دون تعديل الكود المصدري للكلاس، عبر تغليفه بطبقات (wrappers).

مثال واقعي إضافات القهوة: سكر + حليب + كراميل — دون تغيير وصفة القهوة الأصلية.

المشكلة: محرّر نصوص يدعم Bold/Italic/Underline بكل التركيبات. بالوراثة نحتاج كلاس لكل تركيبة (BoldText, ItalicText, BoldItalicText, BoldUnderlineText...) = انفجار في عدد الكلاسات، صعب الصيانة، ويخالف Open/Closed.

PlainText ▲ │ (بدل الوراثة ← استخدم تغليف) TextDecorator - component: IText ▲ ├── BoldDecorator +Render(){ component.Render(); add <b> } ├── ItalicDecorator +Render(){ component.Render(); add <i> } └── UnderlineDecorator Stacking: Client → Underline → Italic → Bold → PlainText Output: <u><i><b>Hello</b></i></u>

لماذا Decorator بدل Inheritance؟ الوراثة ثابتة (compile-time) وتنتج كلاسات كثيرة للتركيبات؛ الـDecorator ديناميكي وكل wrapper مسؤولية واحدة، يمكن تركيبها بأي ترتيب بأقل عدد كلاسات.

الأنماط السلوكية — Strategy و Observer Behavioral Patterns — Strategy & Observer

الأنماط السلوكية تركّز على كيفية تفاعل الكائنات وتوزيع المسؤوليات.

1) Strategy — الاستراتيجية Behavioral

التعريف: يعرّف عائلة من الخوارزميات، يغلّف كل واحدة في كلاس منفصل، ويجعلها قابلة للتبديل وقت التشغيل. العميل يختار الخوارزمية دون تعديل الكلاس المستخدم.

التحفيز: نظام تسوّق يقبل Visa/MasterCard/PayPal/Apple Pay/Cash. كيف نصمّمه؟

الحل السيّئ — كل شيء في كلاس واحد وضع كل بوابات الدفع في كلاس واحد بـ if-else ضخم. إضافة Google Pay أو Crypto يتطلّب تعديل الكلاس = يخالف Open/Closed، if-else ضخمة، اختبار صعب، صيانة صعبة.
IPaymentStrategy (interface) ▲ ┌──────────┼──────────┐ │ │ │ Visa PayPal ApplePay (ConcreteStrategies) ShoppingCart (Context) — يحوي مرجعاً لـ IStrategy ★ لا يعرف تفاصيل الدفع، فقط Pay()

المشاركون (3):

Strategy (interface)
يعرّف الخوارزمية، مثل IPaymentStrategy.
Concrete Strategy
تنفيذ الخوارزمية: VisaPayment، PayPalPayment.
Context
الكلاس المستخدم: ShoppingCart. يحوي مرجعاً للاستراتيجية ولا يعرف تفاصيلها.
✓ استخدمه عند
  • خوارزميات متعددة تحلّ نفس المشكلة.
  • تجنّب if-else أو switch الكبيرة.
  • الحاجة لتبديل السلوك وقت التشغيل.
أمثلة شائعة
  • بوابات الدفع.
  • حساب الشحن / الضريبة.
  • خوارزميات الفرز.
  • ضغط البيانات.
  • طرق المصادقة.

2) Observer — المراقِب Behavioral

التعريف: يعرّف علاقة one-to-many بين الكائنات، بحيث عند تغيّر حالة كائن واحد، تُبلَّغ كل الكائنات المعتمدة عليه تلقائياً.

أمثلة واقعية إشعارات Facebook · مشتركي YouTube (عند رفع فيديو، كل المشتركين يصلهم إشعار) · تطبيقات الطقس · تطبيقات سوق الأسهم.

سيناريو مقهى: حالة الطلب تتغيّر من «جارٍ التحضير» إلى «جاهز». يجب إبلاغ: شاشة العرض + تطبيق العميل + SMS + الإيميل + التحليلات — تلقائياً، دون نداء كل خدمة يدوياً.

CoffeeOrder (Subject) │ on "Ready": NotifyAll() ▼ [ Observer List ] ├── OrderDisplay → Update() ├── CustomerApp → Update() ├── SmsService → Update() ├── EmailService → Update() └── AnalyticsService → Update() ★ Subject لا يعرف من هم المراقبون، فقط يبلّغهم

المشاركون:

Subject
يسجّل/يحذف/يبلّغ المراقبين. مثل CoffeeOrder.
IObserver
interface يعرّف ميثود Update().
Concrete Observers
تنفيذات: OrderDisplay، CustomerApp، SmsService...
✓ إضافة مراقب جديد لإضافة EmailService جديد: أنشئ كلاس جديد يطبّق IObserver وسجّله. كلاس CoffeeOrder يبقى دون تعديل = تطبيق نموذجي لـ Open/Closed Principle.

الـClean Architecture و الـDependency Injection Clean Architecture & Dependency Injection

هام للنصفي قد لا يكون L5 ضمن نصفي بشكل كامل، لكن مفاهيمه (خاصة Dependency Inversion من SOLID و فصل الطبقات) قد تظهر. هذا أكثر قابلية للتأخّر للنهائي.

هندسة البرمجيات هي البنية عالية المستوى للنظام: كيف تتفاعل المكوّنات وتتصل لتلبية أهداف العمل. البنية الجيدة تكون: قابلة للصيانة، للتوسّع، للاختبار، مرنة، آمنة، مستقلّة.

مبدأ Separation of Concerns · فصل الاهتمامات

تقسيم النظام لأجزاء مستقلّة، كل جزء له مسؤولية واحدة. هذا أساس كل بنية نظيفة.

مشكلة الـN-Tier التقليدية · Layered Architecture Problems

Presentation ▼ Business ◆ يعتمد مباشرة على قاعدة البيانات! ▼ Data Access ▼ SQL Server
المشاكل منطق العمل يعتمد مباشرة على قاعدة البيانات → صعب الاختبار، صعب التبديل، اقتران عالٍ، التغييرات تؤثر على ملفات كثيرة. Transitive Dependency: تغيير صغير في DB ينتشر صعوداً لكل الطبقات.

الحل: Database-Centric ← Domain-Centric · قلب النظام

التفكير التقليدي: قاعدة البيانات هي قلب النظام (Database-Centric). التفكير الحديث: الـBusiness (Domain) هو قلب النظام، وقاعدة البيانات مجرد أداة تخزين.

ما هي الـClean Architecture؟ · What is Clean Architecture?

بنية برمجية اقترحها Robert C. Martin (Uncle Bob). الهدف الرئيسي: «قواعد العمل يجب ألا تعتمد على التفاصيل التقنية الخارجية». قاعدة البيانات، الـUI، الـAPIs، والـFramework يمكن أن تتغيّر، لكن منطق العمل يبقى مستقراً.

القاعدة الذهبية: الاعتمادية تتّجه للداخل فقط · The Dependency Rule

Presentation (API / UI) ──┐ ▼ │ Application (Use Cases) │ تعتمد للداخل ▼ │ Domain (Business Rules) ◀────┘ ★ القلب Infrastructure (DB, APIs) ──▶ تعتمد على Application & Domain ★ الطبقات الداخلية لا تعرف شيئاً عن الخارجية

الطبقات الأربع · The Four Layers

1. Domain · النواة
الطبقة الأعمق والأهم. تحتوي Entities، Value Objects، قواعد العمل. لا تعتمد على أي شيء — لا DB ولا framework.
2. Application · التطبيق
حالات الاستخدام (Use Cases) + DTOs + Repository interfaces. تنسّق كائنات Domain. لا تعرف SQL.
3. Infrastructure · البنية التحتية
تفاصيل تقنية: EF Core، SQL Server، APIs خارجية، Email/SMS. تنفّذ interfaces الـApplication.
4. Presentation · العرض
نقطة الدخول: Controllers، HTTP requests/responses. لا تحوي منطق عمل.

Entity مقابل Data Model · Entity vs Data Model

مفهوم خاطئ شائع الظنّ أن Entity = جدول قاعدة بيانات. هذا خطأ. Entity تمثّل مفهوم عمل، والجدول مجرد طريقة واحدة لحفظها.
✗ Anemic Domain Model
  • الكيان يخزّن بيانات فقط.
  • منطق العمل في مكان آخر.
  • ضعيف — لا يحمي قواعده.
✓ Rich Domain Model
  • منطق العمل داخل الـEntity.
  • الـEntity يحمي حالته بنفسه.
  • Balance له private set، التعديل عبر Deposit() فقط.

Dependency Injection (DI) · حقن الاعتمادية

ASP.NET Core يوفّر DI container مدمج يُنشئ الكائنات ويحقنها تلقائياً عند الحاجة. التسجيل في Program.cs: 

builder.Services.AddScoped<IAccountRepository, AccountRepository>();
builder.Services.AddScoped<IAccountService, AccountService>();

// عند طلب IAccountRepository يُنشأ AccountRepository تلقائياً ويُحقن

أعمار الخدمات (Service Lifetimes):

Transient
كائن جديد لكل طلب. للخدمات الخفيفة. AddTransient()
Scoped
كائن واحد لكل HTTP request. الأكثر شيوعاً. AddScoped()
Singleton
كائن واحد للتطبيق كله. للـCache، Logger، Config. AddSingleton()

تدفّق طلب كامل · Complete Request Flow

HTTP Request: POST /api/accounts/transfer ▼ Controller (Presentation) ▼ Application Service (Use Case) ▼ Domain Entity (Business Rules) ▼ Repository (Interface from Application) ▼ SQL Server (Infrastructure)

🏭 Singleton C
نسخة واحدة + نقطة وصول عامة. private ctor + static method. مثال: Logger. يخالف SRP.
🏭 Factory Method C
يفوّض الإنشاء لـmethod بدل new. subclasses تقرر النوع. اقتران ضعيف.
🏗️ Adapter S
Translator بين واجهتين. Client · ITarget · Adapter · Adaptee. مثال: محوّل كهرباء.
🏗️ Facade S
واجهة مبسّطة لنظام معقّد. العميل يتحدث مع Facade فقط. مثال: «شاهد فيلم».
🏗️ Proxy S
بديل يتحكم بالوصول: أمان، lazy load، cache. مثال: بطاقة ATM.
🏗️ Decorator S
تغليف ديناميكي يضيف سلوكاً بلا وراثة. مثال: إضافات القهوة.
🧠 Strategy B
عائلة خوارزميات قابلة للتبديل وقت التشغيل. IStrategy · Concrete · Context. مثال: طرق الدفع.
🧠 Observer B
one-to-many + إبلاغ تلقائي. Subject · IObserver · Concrete. مثال: مشتركي YouTube.
